# Показ проекта жюри через Burp Repeater

Готовы веб-кабинет, FastAPI, SQLite, вход и роли, создание сотрудников, создание и распределение заявок, статусы, обязательный результат закрытия, история, фильтры и статистика. Telegram-бот пока не создан, связь Telegram → сайт → Telegram сегодня не показываем как готовую.

## Быстрый путь через браузер Burp

1. Откройте Burp → Proxy → Open browser, выключите Intercept, чтобы запросы не зависали в ожидании Forward.
2. В открытом браузере перейдите на `http://127.0.0.1:3000`, войдите администратором и создайте заявку или исполнителя.
3. В Proxy → HTTP history выберите соответствующий запрос `/api/...`, правой кнопкой → Send to Repeater. В Repeater изменяйте JSON и нажимайте Send. Cookies и CSRF-заголовок уже будут в захваченном запросе.

Этот путь показывает настоящее взаимодействие вебки с API через Next.js proxy. Не смешивайте его с прямым API на порту 8000: cookies и Origin следует брать от того же сеанса и адреса.

## Ручные запросы к API

Установите target в Repeater: **host `127.0.0.1`, port `8000`, HTTP, TLS выключен**. Если порт менялся, возьмите его из `.local/processes.json`. Для прямых запросов API в шаблонах Origin не нужен. HTTP/1.1 подходит. Оставьте включённым автоматическое обновление Content-Length: Burp пересчитает длину после замены JSON и паролей.

Официальные инструкции: [отправка HTTP в Repeater](https://portswigger.net/burp/documentation/desktop/tools/repeater/http-messages), [настройка Update Content-Length](https://portswigger.net/burp/documentation/desktop/settings/tools/repeater).

В `docs/burp-requests/` лежат отдельные сырые HTTP-запросы `.txt`. Копируйте **содержимое одного файла** в редактор запроса Repeater. Не отправляйте весь набор как один запрос.

Маркеры `{{SESSION}}`, `{{CSRF}}`, `{{TICKET_ID}}`, `{{VERSION}}`, `{{EXECUTOR_ID}}`, `{{OTHER_EXECUTOR_ID}}`, `{{PASSWORD_FROM_ENV}}`, `{{CHOOSE_EXECUTOR_PASSWORD}}` — места для ручной замены, а не переменные Burp. Заменяйте маркер целиком, включая фигурные скобки. Названия заголовков, например `X-CSRF-Token`, не меняйте. В JSON поля id/version остаются числами без кавычек.

### 1. Готовность и вход

`01-health.txt` → Send. Ожидается 200 и `{"status":"ok","database":"ok","notifications":"disabled"}`.

`02-login.txt`: замените `PASSWORD_FROM_ENV` паролем администратора из `backend/.env`, ключ `BOOTSTRAP_ADMIN_PASSWORD`. Логин берите из `BOOTSTRAP_ADMIN_LOGIN` (по умолчанию admin). Если пароль уже меняли через кабинет, используйте новый пароль. Значения .env после административной смены сами не обновляются.

```http
POST /api/auth/login HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json
Connection: close

{"login":"admin","password":"PASSWORD_FROM_ENV"}
```

Ожидается 200. В **заголовках ответа** найдите два `Set-Cookie`:

```text
Set-Cookie: shkola_session=<значение>; HttpOnly; ...
Set-Cookie: shkola_csrf=<значение>; ...
```

Возьмите только значения до первой `;`. Во всех следующих файлах замените SESSION и CSRF:

```http
Cookie: shkola_session=SESSION; shkola_csrf=CSRF
X-CSRF-Token: CSRF
```

Не рассчитывайте, что Repeater автоматически подставит Set-Cookie из предыдущего ответа. Вход ограничен 10 попытками за 5 минут, поэтому войдите один раз и используйте ту же сессию. Не включайте реальные cookies или пароли в публичные материалы защиты.

### 2. Сотрудники и классификаторы

`03-staff.txt` → 200: список сотрудников с реальными ID. `04-categories.txt` → 200: группы и вложенные элементы. Возьмите ID активной группы и принадлежащего ей активного элемента; начальная пара — group_id=1, item_id=1, если справочники не менялись.

`05-create-executor.txt`: задайте уникальный `login` (при повторной демонстрации измените его), имя и свой пароль длиной 10–128 символов. `role="operator"` означает исполнителя с возможностью работать в кабинете.

```json
{"name":"Исполнитель демонстрации","login":"jury_executor","password":"CHOOSE_EXECUTOR_PASSWORD","role":"operator"}
```

Ожидается **201**. Скопируйте `id` ответа как EXECUTOR_ID. Исполнитель сразу появляется в вебке в разделе «Сотрудники» и в списке назначения. При повторном логине будет 409 — это защита от дублей, а не сбой.

### 3. Оформление обращения

`06-create-ticket.txt` → 201. Укажите имя заявителя, контакт, group_id, item_id и описание. Пример — неработающий проектор в кабинете 204. Источник будет `web`; имитации заявки Telegram здесь нет.

Из ответа сохраните **id, number и version**. Номер показывайте жюри; внутренний id используйте в URL. VERSION берите из ответа, не предполагайте, что она начинается с 1.

### 4. Работа и распределение

`07-take.txt`: замените TICKET_ID в URL и VERSION в JSON:

```json
{"action":"take","version":VERSION}
```

Ответ 200, статус `in_progress`, исполнитель — текущий вошедший сотрудник. Скопируйте новую version.

`08-assign.txt`:

```json
{"action":"assign","assignee_id":EXECUTOR_ID,"version":VERSION}
```

Ответ 200, текущий исполнитель — созданный сотрудник. **Назначение сохраняет статус.** Оно работает и с новой заявкой, но последующее действие «Взять в работу» назначает именно текущего пользователя. В этом коротком сценарии все действия выполняет администратор, поэтому сначала take, затем assign.

`09-reassign.txt` — необязательно: укажите ID другого активного сотрудника из `03-staff.txt` и последнюю version. Новая запись истории сохранит предыдущего и нового исполнителя. При назначении тому же человеку событие не создаётся и version не меняется.

### 5. Закрытие и подтверждение результата

`10-complete.txt`: последняя version и непустой комментарий:

```json
{"action":"complete","version":VERSION,"comment":"Заменён кабель HDMI. Проектор проверен и работает."}
```

Ответ 200: `status=completed`, заполнены `result` и `closed_at`.

`11-ticket-history.txt` → 200: карточка и массив history с созданием, взятием, назначением/переназначением и закрытием. `12-stats.txt` → 200: реальные счётчики и распределение. Откройте сайт и обновите список — то же обращение и результат находятся в той же SQLite.

`13-unassigned.txt` показывает обращения без исполнителя; `14-executor-tickets.txt` — только обращения выбранного исполнителя. Если закрытое обращение назначено этому сотруднику, оно тоже входит в его список: фильтр по статусу задаётся отдельно.

### 6. Короткие отрицательные проверки

- `15-no-session.txt`: без cookies получите 401.
- `16-no-csrf.txt`: с рабочей сессией, без CSRF на изменяющем запросе получите 403.
- Для **отдельной заявки в работе** отправьте complete без comment: получите 422. После добавления результата — 200.
- Повторите уже успешный запрос со старой VERSION: получите 409, конкурентные изменения не затрутся. Для ещё открытой заявки получите свежую версию через GET и повторите корректное действие.
- Из новой заявки попробуйте complete с комментарием: получите 409, сначала требуется взять её в работу.
- Закрытая заявка остаётся читаемой, её изменение возвращает 409.

## Что говорить жюри

«Сотрудники входят в веб-кабинет с ролями оператора и администратора. Администратор создаёт исполнителей. Классификатор описывает тему обращения: например, Оборудование → Проектор. Заявка получает уникальный номер и сохраняется в SQLite. Её можно назначить сотруднику и переназначить, все действия фиксируются в истории. Сервер проверяет переходы статусов, обязательный результат и версию записи. Статистика строится по базе. Готовый сегодня канал ввода — веб-форма и API; Telegram — следующий этап».

Классификатор не назначает сотрудника автоматически: тему выбирают при оформлении, исполнителя — при распределении. Такой порядок соответствует ручному назначению из ТЗ.
