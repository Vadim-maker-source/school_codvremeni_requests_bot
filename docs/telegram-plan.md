# Telegram: реализация

Цель: aiogram 3, long polling, общая PostgreSQL и ticket_service без дублирования бизнес-правил.

Сценарии: группа → элемент → описание → контакт → подтверждение; назад/отмена; номер и статус только своих заявок. Диалог хранится в БД, ключ подтверждения предотвращает дубли.

Привязка: сотрудник в авторизованном кабинете получает одноразовую ссылку на 10 минут; /start связывает доверенный Telegram user ID с его учётной записью. Один ID на одну запись. Есть отвязка. Пароль и произвольный ID в чат не передаются.

Уведомления: create → активные связанные администраторы; assign/take → назначенный связанный сотрудник; take/complete/reject → заявитель. Транзакционный outbox, аренда записи, повтор временных ошибок, terminal failed для постоянных. Проверка актуальности привязки перед отправкой. Доставка через внешнюю сеть допускает повтор после аварии между отправкой и commit.

Порядок: миграция → привязка и outbox → диалог и worker → интерфейс → тесты → запуск.

Приёмка: изолированные тесты диалога, владения, привязки, повторного подтверждения, очереди и ошибок; браузерная привязка; сборка; миграция PostgreSQL; getMe и запущенный polling. Реальная отправка сотрудникам проверяется после запуска ими бота и привязки аккаунта. При доступном Telegram worker опрашивает очередь каждые 3 секунды; фактическую доставку <60 секунд проверяем отдельно.
